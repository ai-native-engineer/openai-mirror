## 開始之前

產品意見回饋可能散布在 Slack、問卷匯出資料、議題追蹤系統、客服紀錄或研究筆記中。請向 ChatGPT Work 提供要審查的資料來源、產品範圍和日期範圍。它可以將反覆出現的問題整理到試算表或文件中，供團隊在決定下一步之前檢查。

請在 Web 版或桌面版 Work 中，使用已連線的應用程式和雲端檔案啟動此工作流程。如果資料來源位於你的電腦上，請先附加本機匯出資料，或使用桌面版 App。

## 預期結果

這個範例使用請求審查佇列的問卷匯出資料、客服紀錄、意見回饋討論串和研究筆記。初步分析會將反覆出現的問題分組；後續步驟則把一個範圍過廣的主題拆成兩項更明確的決策。

<div data-use-case-export-only>

初步分析在問卷、客服紀錄、意見回饋討論串和研究筆記這四個資料來源中，發現三個反覆出現的問題：

- **佇列中未顯示衝突：** 四個資料來源共提及八次。在清單中顯示衝突狀態，並區分 `Ready` 與 `Needs attention`。
- **批次核准可能包含遭封鎖的請求：** 四個資料來源共提及四次。預設略過遭封鎖的請求，或在核准前發出警告。
- **審查人員會失去原本的瀏覽位置，也無法單獨篩出工作項目：** 四個資料來源共提及十次。保留搜尋內容與篩選條件，並提供 `Needs attention` 檢視畫面。

後續步驟將最後一個主題拆分後，表格會區分 **返回佇列後搜尋內容和篩選條件遭重設** 與 **難以單獨篩出遭封鎖和未審查的工作項目**。表格會為每個主題保留受影響的使用者、佐證 ID、信心水準、對設計的影響、待釐清問題和後續行動。這些數字代表小型樣本中反覆提及的次數，而非整體產品的發生率。

## 運作方式

1. 向 Work 提供要審查的意見回饋來源、產品範圍和時間範圍。
2. 請它將反覆出現的意見回饋歸納成主題，並為每個主題保留佐證連結或 ID。
3. 建立一份 Google 試算表或文件，列出受影響的使用者、信心水準、待釐清問題，以及需要做出的決策或後續行動。
4. 將任何主題轉成 Slack 更新內容或議題草稿之前，請先審查摘要。

先使用本頁的起始提示詞進行初步分析，再細化範圍過廣、缺少佐證或混合了不同問題的主題。

## 將已審查的主題轉成下一份草稿

摘要完成後，請 Work 拆分範圍過廣的主題、補上缺少的佐證、起草 Slack 更新內容，或將已審查的主題轉成議題草稿。請明確說明受眾和所需決策，讓下一步一目了然。

## 讓意見回饋頻道保持最新

對於持續收到新回報的 Slack 頻道或議題佇列，請 Work [依排程檢查](/zh-Hant/codex/automations#schedule-work-from-a-task)。沿用相同的審查界線，避免未經核准就根據新的意見回饋發布貼文、建立議題或指派工作。
