## 使用方式

要求 Codex 檢查錯誤回報原本就會出現的地方：Sentry 警示、Linear 議題、GitHub 議題、PR 檢查、部署記錄、支援工單和 Slack 討論串。先手動巡查一次，在對話中調整報告，然後按排程執行。

使用同一個 Codex 對話完成整個錯誤分流流程：

1. 執行一次隨選巡查並取得清單草稿。
2. 在同一個對話中檢視清單並提供意見。
3. 在該對話中，為分流工作排程一項任務。
4. 選用：確信報告準確時，可要求 Codex 撰寫 Linear 議題、Slack 更新、GitHub 留言或交接備註的草稿。

開始之前，請安裝 Codex 所需的 [外掛程式](/zh-Hant/codex/plugins)，例如 Sentry、Slack、Linear 或 GitHub。在入門提示詞中，將方括號內的外掛程式清單換成實際的 `@` 外掛程式標籤。接著，將方括號內的各個來源換成要搜尋的確切位置：Sentry 專案或警示 URL、Slack 頻道或討論串、Linear 團隊、檢視或查詢、GitHub 程式碼庫、議題查詢或 PR 檢查、部署連結、記錄檔、支援佇列或儀表板。

## 第 1 階段：執行巡查

若測試、程式碼庫工具、建置檢查或 CI 失敗等本機上下文能提供協助，請從這些錯誤所屬的程式碼庫啟動 Codex。如果可透過外掛程式、連接器、MCP 伺服器、連結、匯出資料、貼上的記錄或附件取得錯誤來源，也可以從任何程式碼庫執行巡查。

先執行上方的入門提示詞，只保留巡查所需的外掛程式和資料來源。

例如，填妥的提示詞可以列出外掛程式，以及巡查所需的確切佇列、頻道或程式碼庫。

## 第 2 階段：讓報告更實用

自動化之前，請確認報告確實實用，值得每天查看。

實用的首次執行結果包括：

- 訊息明確的錯誤依 P0 至 P3 排序。
- 重複回報歸入同一個錯誤。
- 每個錯誤都有證據連結或簡短引文。
- 推測與觀察到的事實分開列出。
- 每個錯誤都有簡短的建議後續行動。

在排程前，先於同一個對話中調整報告。你可以要求 Codex：

- 在清單排序前，再檢查一個來源。
- 排除團隊已知、雜訊過多的警示。
- 只傳回 P0 和 P1 錯誤。
- 若 Slack 回報、Sentry 警示和 GitHub 檢查失敗都指向同一個錯誤，便將它們合併。
- 每個錯誤只顯示最合適的單一連結。
- 補充足夠的證據，讓其他人可以重現問題或交由適當的人處理。

## 第 3 階段：將巡查自動化

當隨選報告已足夠實用時，請留在同一個對話中，並 [從該對話為分流工作排程一項任務](/zh-Hant/codex/automations#schedule-a-task-inside-a-chat)。Codex 可以根據你在對話中調整的內容，撰寫週期性執行所需的提示詞。

## 第 4 階段：分派後續工作

確定排程報告實用後，請決定接下來要如何分派工作。Codex 可以為團隊頻道擬定 Slack 更新、為你想追蹤的錯誤撰寫 Linear 議題、為檢查失敗的 PR 撰寫 GitHub 留言，或為值班人員準備交接說明。
