## 簡介

若希望 Codex 持續朝單一且持續有效的目標推進，而非在一般單輪互動後就停止，請使用 `/goal`。這適用於目標明確、具備驗證迴圈，且 Codex 有足夠自主空間持續推進、不必由您逐步指引的工作。使用 `/goal` 後，Codex 可以獨立工作數小時，無需您介入。

使用 `/goal <objective>` 設定目標，使用 `/goal` 查看目前的目標；需要控制執行過程時，請使用 `/goal pause`、`/goal resume` 或 `/goal clear`。

如果 `/goal` 未出現在斜線指令清單中，
請在 `config.toml` 中啟用 `features.goals`：

```toml
[features]
goals = true

您也可以在 CLI 中執行 `codex features enable goals`，或要求 Codex 執行此指令。

## 選擇合適的工作

合適的目標應比單一提示詞涵蓋更多工作，但又要比沒有明確終點的待辦工作清單更聚焦。它應定義 Codex 要達成什麼、不應變更什麼、如何驗證進度，以及何時應停止。

適合的情境包括：

- 目標技術堆疊、功能一致性檢查與限制條件都很明確的程式碼遷移
- Codex 可在每個檢查點後執行測試的大型重構
- Codex 可持續改善可運作成果的實驗、遊戲或原型

請避免把一系列鬆散且彼此無關的工作設為單一目標。

## 設定執行迴圈

1. 明確指定一項目標與一項停止條件。
2. 指定 Codex 必須先閱讀的檔案、文件、議題、紀錄或計畫。
3. 定義可用來證明進度的指令或產出物。
4. 要求 Codex 以檢查點為單位推進工作，並保留簡短的進度紀錄。
5. 執行期間，請使用 `/goal` 查看狀態。
6. 執行完成、受阻或需要改變方向時，請暫停、恢復或清除目標。

關鍵在於約定本身。開始前，Codex 就應知道何謂「完成」。如果目標是遷移，「完成」可能表示新路徑通過契約測試，而且舊有路徑仍保留復原機制。如果目標是遊戲或原型，「完成」可能表示應用程式能夠建置與啟動，並符合提供的參考資料或預期行為。

  請 Codex 協助：先與它討論您想要
建構的內容，再要求它直接設定目標並開始工作。

## 讓 Codex 獨立工作

目標執行期間，請 Codex 提供精簡的進度報告，讓您能更放心地交由它執行。實用的狀態更新應列出目前的檢查點、已驗證的項目、剩餘工作，以及 Codex 是否受阻。
如果狀態變得含糊，應進一步收斂目標，而不是增加更多一次性指示。請明確告訴 Codex 接下來哪個檢查點最重要、哪項指令能證明已達成該檢查點，以及遇到什麼情況時應暫停。

Codex 持續推進目標時，可以連續獨立工作許多小時，無需您定期查看進度。當它確信已達停止條件時便會停止執行，因此您應將 `/goal` 視為不需要監控的背景任務。

## 目標範例

### 遷移

無論是將遊戲遷移至新的技術堆疊、將行動應用程式遷移至新平台，還是將程式碼庫遷移至新框架，您都可以使用 `/goal`，讓 Codex 執行遷移：

### 建立原型

無論您要從零開始建立新的應用程式、遊戲或功能，都可以使用 `/goal`，讓 Codex 完成一個精緻的第一版。您可以使用 PLAN.md 檔案引導第一版的開發，並在其中精確說明您要建構的內容。

### 提示詞最佳化

若已有評估套件，您可以使用 `/goal`，依據評估結果最佳化提示詞。Codex 可以檢查失敗案例、更新提示詞、重新執行評估，並持續反覆改善，直到分數提高或達到您設定的停止條件。
