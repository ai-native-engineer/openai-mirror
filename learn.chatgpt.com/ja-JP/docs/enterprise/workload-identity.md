ワークロード ID フェデレーションを利用すると、個人用アクセストークンやその他の長期間有効な OpenAI 認証情報を保存することなく、信頼できる自動化処理から Codex を使用できます。ワークロードは、すでに運用しているプロバイダーから取得した短期の ID トークンを提示します。OpenAI はそのトークンを検証し、管理対象の ChatGPT ワークスペースに属するユーザーまたはサービスアカウント用の短期アクセストークンを返します。

クラウドプラットフォーム、
Kubernetes、CI システムなど、OIDC トークンまたは
SPIFFE JWT-SVID を発行できる環境で Codex プロセスを無人実行する場合は、ワークロード ID を使用してください。共有される信頼モデルと、別個の OpenAI API フローについては、
[ワークロード ID の概要](/api/docs/guides/workload-identity-federation)を参照してください。

  Codex のワークロード ID フェデレーションはベータ版であり、利用するには
  ワークスペースで有効化する必要があります。利用を希望する場合は、OpenAI の担当者または[OpenAI
  サポート](https://help.openai.com/en/articles/6614161-how-can-i-contact-support)にお問い合わせください。

## 開始前の準備

必要なもの：

- OpenAI Admin Portal でワークロード ID を管理する権限
- 管理対象の ChatGPT ワークスペース
- そのワークスペースの有効なメンバーである ChatGPT ユーザーもしくはサービスアカウント、またはセットアップ時にいずれかを作成する権限
- 発行者、オーディエンス、識別用クレームを把握している OIDC トークンまたは SPIFFE JWT-SVID
- 絶対パスにある保護されたファイル内のトークンを最新の状態に維持できるランタイム
- Codex 0.148.0 以降
- ChatGPT 認証と
  フェデレーションルールで選択されたワークスペースを許可する、実際に適用される Codex 認証ポリシー。詳細は[ログイン
  方法またはワークスペースの強制](/ja-JP/codex/auth#enforce-a-login-method-or-workspace)を参照してください。

OpenAI は、トークンの交換時にプリンシパルを作成したり、ワークスペースへのメンバー登録を行ったりしません。管理者は、ワークロードが接続する前にプリンシパルを選択または作成します。人間のユーザーを作成するとワークスペースのシートが 1 つ消費され、そのワークスペースのメンバーシップルールが適用されます。

ネイティブの Windows 環境では、 **権限昇格モード**の
[Windows サンドボックス](/ja-JP/codex/windows/windows-sandbox)を使用してください。それ以外の Windows サンドボックスモードでは、
モデルが制御するコマンドから ID トークンファイルを保護できません。

## ID トークンの取得

ワークロードのランタイムが上流の ID トークンを取得し、更新します。Codex がクラウドのメタデータサービスや ID プロバイダーのクライアントライブラリを代わりに呼び出すことはありません。

| ランタイム                          | トークンファイルの推奨取得元                                                                                                   |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| Kubernetes、AKS、EKS、または GKE     | 投影されたサービスアカウントトークンをマウントし、そのファイルを Codex に指定します。トークンはプラットフォームによってローテーションされます。                                  |
| Microsoft Entra のマネージド ID | Azure IMDS にトークンをリクエストし、有効期限が切れる前にファイルを置き換える、信頼できるホストプロセスまたはサイドカーを実行します。                |
| AWS のアウトバウンド ID フェデレーション | リージョン別の STS `GetWebIdentityToken` を呼び出し、有効期限が切れる前にファイルを置き換える、信頼できるホストプロセスを実行します。                   |
| Google Cloud                     | メタデータサーバーに ID トークンをリクエストし、有効期限が切れる前にファイルを置き換える、信頼できるホストプロセスを実行します。        |
| Oracle Cloud Infrastructure      | インスタンスプリンシパルを使用して IDCS アクセストークンをリクエストし、有効期限が切れる前にファイルを置き換える、信頼できるホストプロセスを実行します。 |
| GitHub Actions                   | ジョブの OIDC トークンをリクエストして保護されたファイルに書き込み、その後のトークン交換の前に新しいトークンをリクエストします。                    |
| SPIFFE                           | SPIFFE Workload API または承認済みのヘルパーを使用して、最新の JWT-SVID をファイルに書き込みます。                                      |
| カスタム OIDC プロバイダー             | 発行者のワークロードフローを使用して JWT を取得し、その JWT の有効期限が切れる前に保護されたファイルを更新します。                            |

- [Google Cloud](/api/docs/guides/workload-identity-federation/google-cloud)

ウェブサイトに貼り付けたり、ログに記録したりしないでください。

## ワークロードの接続

Codex を起動する前に、管理者がプロバイダーとフェデレーションルールを作成します。

1. OpenAI Admin Portal で[ワークロード ID](https://admin.openai.com/workload-identity)を開き、
    **ワークロードを接続**を選択します。
2. Codex 用に構成済みのプロバイダーを再利用するか、新しいプロバイダーを作成します。プロバイダーのプリセットを使用すると、GitHub Actions、Microsoft Entra ID、Google Cloud、AWS、Kubernetes、SPIFFE、およびカスタム OIDC プロバイダーの一般的な設定が自動的に入力されます。
3. **Codex** と、ワークロードが利用できる管理対象のワークスペースを選択します。
4. ワークロードを識別するための、可能な限り限定的な条件を追加します。サブジェクト、完全一致するクレーム、CEL 条件、またはそれらの組み合わせに一致させます。受け入れるオーディエンスを追加して、ルールが受け入れるトークンを制限します。設定したすべてのマッチャーの条件を満たす必要があります。
5. ルールを 1 人の既存の ChatGPT ユーザーまたは 1 つの既存のサービスアカウントにマッピングするか、セットアップ時にいずれかを作成します。
6. プロバイダー、条件、ワークスペース、プリンシパル、スコープ、アクセストークンの
   有効期間を確認します。 **ワークロードを接続**を選択し、続いて **設定をダウンロード**を選択します。

ダウンロードしたファイルには、機密情報ではないフェデレーションルール ID と、Codex が ID トークンを読み取るパスが含まれています。認証情報は含まれていません。

セットアップを自動化するには、[ワークロード ID の Admin
API](/api/docs/guides/workload-identity-federation/admin-api)を使用します。マッチャーの
動作や具体例については、[フェデレーションルール
リファレンス](/api/docs/guides/workload-identity-federation/federation-rules)を参照してください。

### 監査用の識別情報の追加

複数のランタイムインスタンスがフェデレーションルールを共有している場合、トークン発行の監査イベント内で
各インスタンスを識別できます。省略可能な
`OPENAI_WORKLOAD_IDENTITY_CONTEXT` 変数に、文字列としてエンコードした
JSON オブジェクトを設定します：

```bash

  "instance_id": "runner-42",
  "display_name": "payments-prod",
  "labels": {
    "environment": "production",
    "region": "us-west-2"
  }
}'

このオブジェクトには `instance_id` が必須です。`display_name` と、最大
8 個のラベルも含めることができます。エンコード後のオブジェクトのサイズは最大 1,024 バイトです。`instance_id` と
`display_name` は最大 128 文字です。ラベルのキーは最大 64
文字、ラベルの値は最大 256 文字です。

識別子は ASCII の英字または数字で始まる必要があります。値には、その後に
英字、数字、`.`、`_`、`:`、`/`、`@`、`-` を使用できます。ラベルのキーには、英字、
数字、`.`、`_`、`-` を使用できます。

OpenAI は、このコンテキストを検証済みのワークロード ID ではなく、クライアントから申告された監査用の識別情報として扱います。この情報は、認証、認可、ルールの照合、スコープ、レート制限、失効、機能ゲート、メトリクスには影響しません。認証情報、シークレット、個人データ、プロンプト、モデル出力、その他の顧客コンテンツを含めないでください。

コンテキストが有効な場合、
OpenAI はテナント、プロバイダー、フェデレーションルール、`instance_id` をスコープとする安定した帰属 ID を導出します。
アクセストークンには帰属情報としてその ID が含まれますが、コンテキストは含まれません。
トークン発行に成功した際の監査イベントには、その ID と正規化されたコンテキストが含まれます。
コンテキストが制限を超えているか、このスキーマに違反している場合、交換は `invalid_grant` で失敗します。

Codex はプロセスの起動時にコンテキストを読み込み、コンテキスト、ルール ID、トークンファイルのパスを、モデルが制御するシェル、フック、MCP サーバーには渡しません。コンテキストを変更した場合は、Codex を再起動してください。

### トークンファイルの保護とローテーション

管理対象の Linux、macOS、WSL デプロイメントでは、
管理要件の [`permissions.filesystem.deny_read`](/ja-JP/codex/enterprise/managed-configuration#enforce-deny-read-requirements) に、
トークンディレクトリ全体を追加します：

```toml
[permissions.filesystem]
deny_read = ["/var/run/secrets/openai.com"]

この設定により、Codex ホストプロセスが引き続きトークンを交換に使用できる一方で、モデルが制御するコマンドによる、現在有効なトークンや一時的な置換用トークンの読み取りを阻止できます。投影トークンのボリュームでは、トークンのマウント全体と、マウント外にある実体のパスや解決後のターゲットパスへの読み取りを拒否してください。ファイルモードの設定や環境変数の除去だけでは、同じユーザーとして実行される別のプロセスから認証情報を保護できません。ネイティブ Windows では、前述の昇格されたサンドボックスを使用してください。

ファイルを投影しないトークンソースでは、信頼できるホストプロセスを使用し、置換用ファイルを保護されたディレクトリ内に毎回書き込んでから、所定のファイル名にリネームしてください。アトミックなリネームにより、Codex が不完全なトークンを読み取ることを防げます。たとえば、次のホスト側で管理する更新スクリプトを、使用するプロバイダーのトークンコマンドに合わせて調整します。スクリプトを実行する前にディレクトリを用意してください：

```bash
set -eu
TOKEN_DIR="/var/run/secrets/openai.com"
TOKEN_FILE="$TOKEN_DIR/identity-token"
umask 077
TOKEN_TEMP="$(mktemp "$TOKEN_DIR/.identity-token.XXXXXX")"
trap 'rm -f -- "$TOKEN_TEMP"' EXIT
trap 'exit 1' HUP INT TERM
your-identity-provider-command > "$TOKEN_TEMP"
test -s "$TOKEN_TEMP"
mv -f -- "$TOKEN_TEMP" "$TOKEN_FILE"

更新プロセスは、Codex が制御できるシェルやツールの外部で実行してください。
更新中やクリーンアップ中も、読み取り拒否を維持してください。
強制停止によって一時ファイルが残った場合でも、そのファイルは必ず読み取り拒否の対象ディレクトリ内に置いてください。
ワークロード ID の設定を `config.toml` に記載しないでください。

## トークンの有効性の維持

上流のトークンが期限切れになる前に、ID トークンファイルを更新してください。Codex は、新しい OpenAI アクセストークンが必要になるとファイルを再読み込みします。OpenAI トークンは、上流のトークンの有効期限とフェデレーションルールで設定された有効期間の満了時点のうち、早い方で失効し、いかなる場合も有効期間は 1 時間を超えません。

管理者がリプレイ保護を有効にした場合、
上流の各 JWT には一意の `jti` が必要です。交換の前には毎回、新しい `jti` を持つ、新たに発行されたアサーションを書き込んでください。
これは、長時間実行されるプロセスでの更新にも適用されます。
`jti` を持たないアサーションには、リプレイ保護が適用されません。

Codex は、各ホストプロセス内で 1 つのインメモリ交換セッションを共有します。そのプロセス内で同時に実行されるリクエストは、有効な OpenAI アクセストークンを再利用し、有効期限が切れた際には 1 回の更新処理を共有します。プロセスが異なれば交換も個別に行われるため、それぞれのプロセスに、プロバイダーが使用を許可したアサーションが必要です。

## 認証情報の優先順位

ワークロード ID に必要な 2 つの変数は、他のすべての認証情報ソースよりも優先されます：

1. `OPENAI_FEDERATION_RULE_ID` または
`OPENAI_IDENTITY_TOKEN_FILE` のいずれかが設定されている場合、Codex はワークロード ID を選択します。
2. 必須変数が一方しか設定されていない場合、Codex はエラーを返します。API キー、アクセストークン、保存済みのログイン情報にはフォールバックしません。
3. `OPENAI_WORKLOAD_IDENTITY_CONTEXT` だけでは、ワークロード ID は選択されません。
4. 必須の WIF 変数がどちらも設定されていない場合、
   Codex はその利用形態における通常の認証情報ルールを適用します。API キー認証に対応する利用形態では、
   `CODEX_API_KEY` が `codex exec`、
`codex review`、TypeScript SDK、`codex exec-server --remote` で優先されます。
   その他の利用形態では、`CODEX_ACCESS_TOKEN` または保存済みのログイン情報を使用できます。

SDK の `apiKey` オプションは `CODEX_API_KEY` に変換されますが、
必須の WIF 変数がいずれか 1 つでも設定されている場合は、WIF が優先されます。
ワークロードで未使用の長期間有効な認証情報を保持しないよう、WIF を使用する際はこのオプションを省略してください。

既存のワークロードを停止せずに移行するには、現在の認証情報がまだ利用可能な状態で WIF を構成します。必須の 2 つの WIF 変数を設定して新しいプロセスを起動してください。以前の認証情報が残っていても、WIF が優先されます。WIF でワークロードが正常に動作したら、以前の認証情報をランタイムとシークレットストアから削除してから、失効させます。失効させる前であれば、必須の WIF 変数を 2 つとも削除して新しいプロセスを起動することで、ロールバックできます。

## 対応する Codex の利用形態

ワークロード ID は、Codex プロセスを実行するマシン上で構成してください。

| 利用形態                                         | 対応状況とホストの境界                                                                               |
| ----------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| 対話型の `codex`、`resume`、`fork`       | 対応しています。構成済みの環境で CLI を起動してください。                                                 |
| `codex exec`、`exec resume`、`codex review` | 対応しています。必須の WIF 変数がいずれか 1 つでも設定されていれば、WIF が優先されます。                                      |
| TypeScript SDK                                  | 対応しています。親プロセスが必須の WIF 変数を提供し、必要に応じて帰属コンテキストも渡します。 |
| `codex app-server`                              | 対応しています。WIF はリモートクライアントではなく、app-server ホストで構成してください。                                |
| `codex exec-server --remote`                    | リモート環境レジストリへの認証に対応しています。WIF は exec-server ホストで構成してください。 |
| ローカルの exec-server プロセスのオペレーション            | WIF 認証は使用しません。ローカルの exec-server プロトコルを通じて実行されます。                         |
| `codex mcp-server`                              | 対応していません。                                                                                          |

app-server および exec-server のリモートクライアントは、それぞれのプロトコルを介して上流の ID トークンを送信することはありません。

## アクセス権の変更と削除

ルールのサブジェクト、オーディエンス、クレーム、CEL 条件、スコープ、トークンの有効期間に対する変更は、新しい交換から適用されます。変更前に発行されたトークンは、有効期間が終了するまで有効な場合があります。

アクセスを直ちに停止するには、プロバイダーまたはルールを無効化してください。無効化すると、新しい交換がブロックされ、そのリソースを通じてすでに発行された OpenAI アクセストークンも失効します。アーカイブも同様にアクセスを停止しますが、元に戻すことはできません。プロバイダーの信頼設定を変更した場合も、新しい信頼設定が有効になる前に、発行済みのトークンが失効します。

## 変更の監査

プロバイダーとフェデレーションルールの作成、更新、アーカイブにより、監査イベントが生成されます。
[Compliance API
と監査イベントのガイダンス](/ja-JP/codex/enterprise/compliance-api)を参照して、ワークスペースが対応しているイベントをエクスポートしてください。
これらのイベントを ID プロバイダーの発行ログと照合し、
上流のアサーションや OpenAI アクセストークンを、いずれのシステムにも記録しないでください。

プロセスが `OPENAI_WORKLOAD_IDENTITY_CONTEXT` を提供する場合、
トークン発行に成功した際の監査イベントには、前述の安定した帰属 ID に加えて、
正規化されたコンテキストも含まれます。

## トラブルシューティング

| 症状                                                               | 確認事項                                                                                                              |
| --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| Codex がワークロード ID の構成不備を報告する              | 同じプロセス内で必須の変数を両方設定し、トークンファイルには絶対パスを使用してください。                               |
| Codex が、ログインポリシーでワークロード ID が許可されていないと報告する | 適用中のポリシーで ChatGPT 認証を許可し、許可対象のワークスペースにルールのワークスペースを含めてください。 |
| Codex が別の認証情報を報告する                                      | 必須の 2 つの WIF 変数を Codex プロセスに読み込み、新しいプロセスを起動して `codex login status` を再実行してください。  |
| OpenAI がワークロードのコンテキストを拒否する                                       | JSON の構造、サイズ、使用可能な文字、フィールドの制限を確認してください。機密情報や顧客コンテンツを削除してください。            |
| OpenAI がトークンを拒否する                                              | `iss`、`aud`、有効期限、署名鍵、アサーションの有効期間をプロバイダーの構成と照合してください。               |
| ルールが一致しない                                               | クライアントが想定どおりのルール ID を使用し、サブジェクト、オーディエンス、クレームの完全一致、CEL の各チェックをすべて通過することを確認してください。  |
| OpenAI がプリンシパルを拒否する                                          | ユーザーまたはサービスアカウントが有効であり、選択したワークスペースの有効なメンバーであることを確認してください。                   |
| OpenAI が再利用されたアサーションを拒否する                                   | 新しい `jti` を含む新しい JWT を取得し、同じリプレイ保護対象のアサーションを使って再試行しないでください。                                  |
| 長時間実行中のプロセスで更新が停止する                               | ホストの更新プロセスが、有効期限が切れる前にトークンファイルを引き続き置き換えていることを確認してください。                                  |

プロバイダーの検証、制限、および CEL の詳細については、[フェデレーションルール
リファレンス](/api/docs/guides/workload-identity-federation/federation-rules)を参照してください。
