このガイドでは、従業員の入社時に適切な ChatGPT ワークスペースへのアクセス権を付与し、担当業務の変更時にアクセス権を更新し、退職時にアクセス権を削除する手順を説明します。ワークスペースのシート、グループに基づくロール、Codex アクセストークン、独自のアクセス制御を持つ接続先システムも対象です。

シングルサインオン（SSO）は従業員の本人確認を行います。プロビジョニングは従業員をワークスペースに追加します。どちらも、それだけで従業員のシート、機能の利用権限、ローカルランタイムのポリシー、外部システムへのアクセス権が決まるわけではありません。

従業員のアクセス権は、ライフサイクルの次の 3 つの節目で管理します。

- **入社：** ワークスペースへのアクセス権、グループ、ロール、適切なシートを設定します。
- **異動：** 従業員の所属グループを更新し、直接割り当てられたロールのうち不要になったものだけを削除します。
- **退職：** ワークスペースへのアクセス権を削除し、トークンを失効させ、接続先システムを確認します。

## 前提条件の確認と担当者の割り当て

従業員の受け入れを始める前に、ライフサイクルの各部分を誰が管理するかを明確にします。

| 担当者                     | 担当業務                                                                                        |
| ------------------------- | ----------------------------------------------------------------------------------------------------- |
| ワークスペースのオーナー           | ディレクトリ同期の有効化、ワークスペースのロールの割り当て、シートタイプの承認、監査情報へのアクセス権の確認 |
| ID 管理者    | ID プロバイダー、アプリケーションの割り当て、プロビジョニンググループの設定と同期状況の管理        |
| ワークスペースの管理者   | ワークスペースのメンバー、グループのメンバー構成、利用可能な管理設定の確認                     |
| セキュリティまたはサービスの責任者 | Codex トークン、接続先システム、共有の自動化処理、必要な監査証跡の確認                |

対象のワークスペースを確認し、必要に応じて組織のメールドメインを検証して、ディレクトリ同期を有効にできるワークスペースのオーナーを特定します。次に、ワークスペースのプランで利用できる管理機能を確認します。

| 機能                                 | 対応するワークスペースのプラン                                                                                    |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------ |
| SCIM によるディレクトリ同期     | ChatGPT Enterprise、Edu、Healthcare                                                                      |
| カスタムロールとロールベースのアクセス制御 | ChatGPT Enterprise、Edu、Healthcare、Teachers                                                            |
| Codex アクセストークン                        | ChatGPT Business、Enterprise                                                                              |
| Codex 専用シート                           | 対象の Enterprise ワークスペースと条件を満たす既存の Business ワークスペース。Edu、Teachers、Healthcare では利用不可 |

SCIM は System for Cross-domain Identity Management の略です。Business ワークスペースでは SCIM に対応していなくても Codex アクセストークンを利用できます。一方、Edu ワークスペースでは Codex アクセストークンや Codex 専用シートに対応していなくても SCIM を利用できます。ご利用のワークスペースで利用可能な管理機能だけを適用してください。

Business ワークスペースで Codex 専用シートを維持・追加できるのは、
2026 年 6 月 24 日より前に Codex シートがあった場合、または同日時点で条件を満たす保留中の Codex シートへの招待があった場合に限られます。
新しい Business ワークスペースや、条件を満たすシートまたは招待がないワークスペースでは、
最初の Codex 専用シートを追加できません。
[ChatGPT Business でのワークスペースのライフサイクルと移行の管理](https://help.openai.com/en/articles/8801890-managing-workspace-lifecycle-and-migration-in-chatgpt-business)を参照してください。

複数のシートタイプに対応するワークスペースでは、
自動プロビジョニングを有効にする前に、**ワークスペース設定 \> ID とアクセス** でデフォルトのシートタイプを確認します。
SCIM でプロビジョニングされたユーザーには、このデフォルトが適用されます。
利用できるプロダクトの画面やアプリはシートによって決まります。
カスタムロールで、そのシートに含まれないアクセス権を付与することはできません。

**権限とロール** で、ローカルアクセス、アクセストークン、
認証情報の有効期間、リモートデバイスに関する設定を確認します。一部のワークスペースでは、
 **Codex と Work のローカル利用**にローカルアクセスの設定がまとめられており、 **メンバーによる Codex と
Work のローカル利用を許可** で制御します。ほかのワークスペースでは、 **Codex のローカル利用**にある **メンバーによる
Codex のローカル利用を許可**と、 **Work のローカル利用**にある **Work をローカルで使用**が分かれています。
Codex と Work の設定が別々の場合、一方を許可しても他方へのアクセス権は付与されません。
トークンの設定は、ローカルアクセスのセクションまたは独立した **アクセス
トークン** セクションに表示されます。これらの設定は、所属グループや
割り当てられたシートタイプとは別です。

次の例では、 **Codex と Work のローカル利用** の設定がまとめられており、
 **アクセストークン** セクションは独立しています。

  

最新の前提条件と対応する ID 管理の構成については、
[ID とプロビジョニング](https://help.openai.com/en/articles/9672121)、
[メンバー、シートタイプ、ロール、アクセス権の管理](https://help.openai.com/en/articles/8266401-managing-members-seat-types-roles-and-access-in-chatgpt-enterprise)を参照してください。

## 従業員のワークスペース参加方法の選択

対象者ごとに、主なプロビジョニング方法を 1 つ選びます。

| 方法                     | アクセス権が付与される仕組み                                                       | アクセス権を削除する場所                                  |
| -------------------------- | ----------------------------------------------------------------------- | ------------------------------------------------------- |
| 手動での招待          | ワークスペースのオーナーまたは管理者が従業員を招待                          | ワークスペースのメンバー管理                         |
| アカウントの自動作成 | 対象のメールドメインを持つ従業員がサインイン                      | ワークスペース管理と関連する ID 管理フロー |
| SCIM によるディレクトリ同期   | ID 管理者が ID プロバイダーで従業員を割り当て | ID プロバイダーのアプリケーションまたはプロビジョニンググループ |

小規模な試験導入や、ディレクトリ同期で管理していないグループには、手動での招待を使用します。従業員の入社、異動、退職に合わせてワークスペースのメンバー構成を ID プロバイダーと連動させる場合は、SCIM を使用します。

アカウントの自動作成と SCIM を同時に有効にしないでください。
アカウントの自動作成で追加されたユーザーは SCIM の管理対象になっていない可能性があるため、
ID プロバイダーのグループから削除しても、ワークスペースへのアクセス権が削除されない場合があります。
最新のガイダンスは、[SCIM 連携に関するよくある質問](https://help.openai.com/en/articles/10011769-openai-platform-scim-integration-faq)を
参照してください。

SCIM では、承認された ID 管理の構成に応じて、単一の ChatGPT ワークスペースまたは組織のテナントを接続できます。各ワークスペースとプロダクトへの割り当てを明確にしてください。ディレクトリ接続を共有していても、すべてのワークスペースや API プラットフォームの組織にわたってアクセス権が自動的に付与・削除されるわけではありません。

## プロビジョニンググループと適切なワークスペースの接続

試験導入の最初の従業員を追加する前に、接続を設定します。ワークスペースのオーナーと ID 管理者では担当業務が異なります。

1. ワークスペースのオーナーに、対象の ChatGPT ワークスペースを選択し、
**ワークスペース設定 \> グループ**を確認してもらいます。既存のグループ名、メンバー、
   カスタムロールの割り当て、関連するプロジェクトや GPT の共有状況を記録します。
2. ID 管理者に、同期対象となる ID プロバイダーのグループを正確に特定してもらいます。その名前とメンバー構成を、ワークスペースにあるすべての既存グループと照合します。
3. 同期対象のグループとワークスペースの既存グループが同じ名前の場合は、同期を有効にする前に、競合するグループの内容を調整するか、名前を変更します。変更後のメンバー、継承されるロール、共有設定について、ワークスペースのオーナーに承認してもらいます。同名の既存グループは SCIM の管理対象となり、そのメンバー構成の管理は ID プロバイダーに切り替わります。
4. 対象範囲を絞った試験導入用のグループを選び、承認されたワークスペース、参加予定の従業員、グループへのロールの割り当てを記録します。
5. ワークスペースのオーナーに、 **ワークスペース設定 \> ID とアクセス**を開き、
    **ディレクトリ同期を有効にする**を選択してもらいます。選択を求められた場合は、ワークスペース単位のプロビジョニングには **このワークスペースでのみ
   SCIM を使用** を、承認されたテナント単位のプロビジョニングには **複数のプロダクトに拡張する
   オプションを維持** を選択します。
   テナント単位の SCIM がすでに有効な場合は、
   2 つ目のワークスペース接続を作成せず、既存の接続を管理します。
6. ID 管理者に、ID プロバイダーとの接続を完了し、ChatGPT アプリケーションを選択して、承認されたグループを割り当ててもらいます。これにより、対象のワークスペースにメンバーがプロビジョニングされます。
7. **ワークスペースの設定 \> グループ**で、選択したグループに SCIM バッジが表示されていることを確認します。
   アクセスの付与に使う前に、グループ名、同期されたメンバー、
   対象のワークスペースを確認します。
8. ワークスペースオーナーに **権限とロール \> カスタムロール**を開き、
   承認済みのロールを作成または選択して、同期されたグループに割り当ててもらいます。
   ロールの構成はウェブで行うことができ、
   ワークスペースオーナーの権限が必要です。
9. 試験導入の代表となる従業員を追加する前に、グループの実効権限とワークスペースのデフォルトのシートタイプを確認します。

ID プロバイダーの管理者はアプリケーションの割り当てとグループのメンバーシップを管理し、
ワークスペースオーナーはディレクトリ同期とワークスペースのロール割り当てを管理します。
プロバイダー別の最新の手順と利用可否については、[SCIM 連携に関するよくある質問](https://help.openai.com/en/articles/10011769-openai-platform-scim-integration-faq)
および[ロールベースのアクセス制御の構成](https://help.openai.com/en/articles/11750701-rbac)
を参照してください。

## 新しい従業員のプロビジョニング

SCIM で管理する従業員には、次の手順を行います。

1. 対象のワークスペース、確認済みメールアドレス、デフォルトのシートタイプ、ID プロバイダーのグループを確認します。
2. ID プロバイダーで、従業員を ChatGPT アプリケーションまたはアクセスを付与するグループに割り当てます。
3. ディレクトリ同期が完了するまで待ちます。従業員が表示されない場合は、ID プロバイダーの現在のステータスを確認します。
4. **ワークスペースの設定 \> メンバー**で、従業員のメールアドレス、
   メンバーシップまたは保留中の招待、シートタイプ、SCIM バッジを確認します。
5. **ワークスペースの設定 \> グループ**で、従業員が対象の同期グループに所属していることを確認します。
   ワークスペースオーナーに、
   そのグループに割り当てられたカスタムロールを確認してもらいます。
6. 代表となる従業員に正しいワークスペースにサインインしてもらい、必要な製品の利用環境、機能、接続先システムを個別に確認してもらいます。
7. 組織で承認された手順に従って、アクセス管理の責任者と検証が成功したことを記録します。

従業員を手動で追加する場合は、ワークスペースのメンバー管理画面から招待を送信し、その後、シート、グループ、ロール、サインインについて同じ確認を行います。

グループはメンバーを整理するためのものであり、グループだけですべての機能へのアクセスが付与されるわけではありません。
ロール割り当ての最新の手順については、
[ロールとワークスペースの権限](/ja-JP/codex/enterprise/roles-and-workspace-permissions)
および[ロールベースのアクセス制御の構成](https://help.openai.com/en/articles/11750701-rbac)を参照してください。

## 従業員のチーム異動に伴うアクセスの更新

チームを異動した従業員に、以前のグループやロールの割り当てによるアクセスが残る場合があります。新しいアクセスレベルを確認する前に、メンバーシップの管理元で次の更新を行います。

1. 従業員の異動先のチーム、必要なワークスペースとシート、承認済みの機能権限、移動先のグループを確認します。
2. 変更中も従業員がワークスペースに所属し続ける必要がある場合は、以前のグループから削除する前に、承認済みの移動先グループに追加します。SCIM で管理するメンバーシップは ID プロバイダーで更新し、手動で管理するメンバーシップはワークスペースの管理画面で更新します。
3. 承認済みのロールが移動先のグループにすでに割り当てられていることを確認します。他のメンバーが承認済みのアクセスを維持できるよう、共有グループの既存のロール割り当ては保持します。
4. グループへのロール割り当てを変更する場合は、ワークスペースオーナーに、グループ全体に適用されるポリシー変更を別途承認し、すべてのメンバーへの影響を確認したうえで変更してもらいます。
5. ワークスペースオーナーに従業員のプロファイルを開いて **直接割り当てロール**を確認し、
   その従業員に直接割り当てられた不要なロールを削除してもらいます。カスタムロールの設定値は **デフォルト**、
**オン**、 **オフ**です。割り当てられたロールのいずれかで明示的に **オフ** が設定されている場合は、
別のロールの**オン** よりも優先されます。
6. チーム異動を承認する前に、直接割り当てられたロールとグループ経由で割り当てられたロールをすべて確認し、従業員の実効権限を確認します。
7. ワークスペースが複数のシートタイプに対応している場合は、ワークスペースオーナーに
**ワークスペースの設定 \> メンバー \> シートタイプの変更** を開き、
   従業員に付与する製品アクセスを確認してもらいます。
8. ChatGPT シートを Codex 専用シートに変更する前に、その従業員がチャット、メモリ、プロジェクト、その他の ChatGPT 機能へのアクセスを失ってよいことを確認します。元のデータは削除されず、従業員を ChatGPT シートに戻すと再び利用できるようになります。
9. 同期と権限の更新が完了したら、新たに許可された操作ができることと、利用できなくなるべき操作ができないことの両方を確認します。

従業員が自動化ワークフローを所有している場合は、その Codex トークン、シークレットマネージャーのエントリ、接続先サービスの認可を、別の承認済みオーナーに移す必要があるか確認します。従業員の Codex のローカル利用権限を削除すると、その従業員の Codex トークンは停止されますが、失効はしません。権限を復元するとトークンが再び有効になるため、アクセスを恒久的に取り消す必要がある認証情報は失効させてください。

## 退職する従業員の削除

まず、従業員のワークスペースのメンバーシップを管理するシステムで対応します。

1. 従業員が SCIM で管理されているか、管理者によって手動で追加されたかを確認します。
2. SCIM で管理されている従業員の場合は、ID プロバイダーでその従業員の ChatGPT アプリケーションへの割り当てを解除し、アクセスを付与するすべてのプロビジョニンググループから削除します。共有グループ自体は削除しないでください。
3. SCIM で管理されていない従業員の場合は、
   ワークスペースオーナーまたは管理者に **ワークスペースの設定 \> メンバー**からそのメンバーを削除してもらいます。
4. 対象のワークスペースにそのメンバーが存在しないことを確認します。SCIM で管理するアクセスの場合は、同期が完了していることと、ID プロバイダーの他の割り当てによってメンバーシップが復元されないことを確認します。
5. 削除の完了を記録し、トークン、接続先システム、保持されているデータを確認する責任者を割り当てます。

ID プロバイダーで従業員が SCIM 管理グループに割り当てられたままの場合は、ワークスペース側の削除だけに頼らないでください。後の同期で、その従業員がワークスペースに再追加される可能性があります。

### Codex アクセストークンの失効と自動化の引き継ぎ

ワークスペースからメンバーを削除しても、信頼された自動化で使う認証情報の確認を省くことはできません。この手順は、ワークスペースが Codex アクセストークンに対応し、その機能が有効になっている場合にのみ適用してください。

Codex のローカル利用権限を削除すると、既存のトークンは停止されますが、失効はしません。ワークスペースオーナーが権限を復元すると、そのトークンは再び使えるようになるため、アクセスを恒久的に取り消す必要がある認証情報は明示的に失効させてください。

**アクセストークン** ページでは、各トークンの作成者とステータスを確認できます。
有効なトークンのアクセスを取り消すには、**失効** を使います。

  

1. ワークスペースオーナーまたは管理者に
[アクセストークン](https://chatgpt.com/admin/access-tokens)を開いてもらいます。
2. 退職する従業員が作成したトークンと、それらのトークンを使っているワークフローを特定します。
3. 切り替え先のアカウントを選びます。対象の従量課金プランで
   長期運用する自動ワークフローには、承認済みの専用[サービス
   アカウント](/ja-JP/codex/enterprise/service-accounts)を使います。それ以外の場合は、
   有効なアカウントを持つ承認済みのワークフローオーナーを特定します。必要に応じて、ワークスペースオーナーに
   その人へのアクセストークン作成権限の付与を依頼し、
   Codex のローカル利用権限もあることを確認します。
4. 新しいトークンを作成します。権限を持つサービスアカウントの運用担当者は、
   サービスアカウントの詳細ページからトークンを作成できます。個人のアカウントに切り替える場合は、
   新しいワークフローオーナーに、自身の
   ChatGPT ワークスペースアカウント用のトークンを作成してもらいます。ダイアログに **スコープ**が表示される場合は、
**Codex** を選択します。他のスコープは、ワークフローに必要な場合にのみ選択してください。
    **スコープ** がないダイアログでは、Codex 専用トークンが作成されます。管理者が
   他のユーザーに代わって個人用トークンを作成することはできません。
5. ワークフローに保存されているシークレットを更新し、新しいトークンで正常に実行できることを確認します。
6. ワークスペースオーナーまたは管理者に、退職する従業員のトークンと、置き換えたすべての旧認証情報を失効させてもらいます。
7. 失効したトークンでは、認証を必要とする新しい実行を開始できないことを確認します。

承認済みの後任オーナーがトークンを作成する際は、ワークフローの内容がわかる名前を付け、
組織のポリシーで許可される最短の認証情報の有効期間を選択します。
 **スコープ** が表示される場合は **Codex** を選択し、
ワークフローに不要な権限は付与しないでください。次の例は、スコープを指定できる画面です。

  

ワークスペースオーナーと管理者は、ワークスペース内の任意のトークンを失効させることができます。
アクセストークンの権限を持つメンバーが失効させられるのは、自分が作成したトークンだけです。
トークンの権限とローテーション手順の最新情報については、
[アクセストークン](/ja-JP/codex/enterprise/access-tokens#rotate-or-revoke-a-token)を参照してください。

### 接続先システムと保持データの確認

ワークスペースのプロビジョニングでは、すべてのシステムの認可範囲を管理するわけではありません。該当するサービスの責任者に、次の対象へのアクセスを確認してもらいます。

- ソースリポジトリと接続された GitHub アカウント
- Google Drive、Slack、その他の接続されたアプリケーション
- インストール済みのプラグイン、同梱のスキル、コネクタを通じて提供される機能
- ホスト型の Codex 環境、共有の自動化、保存されたシークレット
- 管理対象デバイス、ローカルに保存された認証情報、サポート対象のリモートセッション
- 別途管理される Platform API の組織、プロジェクト、API キー

ワークスペースのグループや SCIM の変更によって、
すべてのシステムの権限が更新されると考えず、各システムの管理機能を使って対応してください。
権限の管理範囲の全体像については[ロールとワークスペースの権限](/ja-JP/codex/enterprise/roles-and-workspace-permissions)を、
プラグインの利用可否、同梱のスキル、接続されたアプリの権限については[プラグインの制御](/ja-JP/codex/enterprise/apps-and-connectors)を
参照してください。

ワークスペースへのアクセスを削除することと、コンテンツを削除することは異なります。メンバーが離脱すると、ワークスペースはそのメンバーのプロジェクトとカスタム GPT の所有権をワークスペースオーナーに自動的に移します。これらの項目は削除対象にはなりません。メンバーが再参加すると、所有権はそのメンバーに戻ります。

エンタープライズと Edu のワークスペースでは、チャット、ファイル、canvas ドキュメントに、
ワークスペースに設定された保持ポリシーが適用されます。Business ワークスペースでは、
チャット、ファイル、canvas ドキュメントが無期限に保持されます。Healthcare ワークスペースにも
データ保持の管理機能があります。該当するワークスペースの構成と
[ヘルスケア向け ChatGPT のガイダンス](https://help.openai.com/en/articles/20001046-chatgpt-for-healthcare)を確認してください。

プロジェクトや GPT の所有権を移しても、元メンバーの非公開の会話やファイルは移管されません。
また、ワークスペースオーナーが所有権の変更によって
その非公開コンテンツを閲覧できるようになることもありません。プラン別の現在の動作については、
[ワークスペースのメンバー削除とデータ保持](https://help.openai.com/en/articles/8266418)
を参照してください。

セキュリティやコンプライアンスの要件として変更の証跡が必要な場合は、
対象のワークスペース、従業員、ID プロバイダーでの割り当て、完了時刻、
承認責任者、トークンの失効確認の結果を、承認されたシステムに記録します。
利用できる記録、管理者権限、保持については、
認証が必要な [Admin API リファレンス](https://chatgpt.com/admin/api-reference)で確認します。
機密性の高いコンプライアンス関連のスコープには、ワークスペースオーナーの権限が必要な場合があります。
製品の概要は、[Compliance API と監査イベント](/ja-JP/codex/enterprise/compliance-api)を参照してください。
このガイドから、記録されるイベントの範囲、フィールド、保持期間を推測しないでください。

## アクセス権の不足や想定外の付与に関するトラブルシューティング

| 症状                                               | 確認事項                                                                             | 対処方法                                                                                                       |
| ----------------------------------------------------- | ----------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| 従業員がサインインできても、ワークスペースを見つけられません。  | 対象のワークスペース、招待、ID プロバイダーでの割り当て、メールアドレス         | 割り当てやメールアドレスのマッピングを修正し、ワークスペースに所属していることを確認します。                                               |
| 同期された従業員に誤ったシートが割り当てられます。       | ワークスペースのデフォルトのシートタイプと現在のメンバー情報                     | ワークスペースオーナーに、デフォルトの設定と、その従業員に割り当て可能なシートの選択肢を確認してもらいます。                                     |
| チームを異動しても、機能を引き続き利用できてしまいます。                | ほかのグループへの所属、 **直接割り当てられたロール**、従業員の権限をすべて合わせた実効権限        | 従業員を所属する必要がなくなったグループから削除し、その従業員に直接割り当てられた不要なロールだけをワークスペースオーナーに削除してもらいます。 |
| 手動で管理しているグループが、承認なしに SCIM 管理に切り替わります。  | 同じ名前のグループ、ID プロバイダーのメンバー、継承されたロール、既存の共有設定    | ID プロバイダーでグループの所属を承認済みの内容に合わせて調整し、影響を受けるアクセス権をレビューします。                                 |
| チームの異動後に、ほかの従業員がアクセスできなくなります。       | 共有グループへのロール割り当ての最近の変更内容と、異動前のチームで承認されているアクセス権     | ワークスペースオーナーに、共有グループのロールを承認済みの状態に戻してもらい、その後、異動する従業員のグループ所属だけを更新します。        |
| チームの異動後に、自動化用のトークンが機能しなくなります。 | ワークフローのオーナーに付与された Codex のローカル利用権限と、現在のトークンの状態                      | ワークスペースオーナーに、承認済みの Codex のローカル利用権限を復元してもらうか、該当トークンを新しいものに置き換え、元のトークンを失効させます。                     |
| アクセス権の変更がすぐに反映されません。           | ID プロバイダーの同期状況、想定される同期所要時間、最近のロール更新          | OpenAI サポートに問い合わせる前に、ID 管理者に同期状況を確認してもらいます。                                        |
| 削除した従業員がワークスペースに再追加されます。           | ID プロバイダーでのアプリケーションの割り当てと、アクセス権を付与するすべてのプロビジョニンググループ | ワークスペースの設定で削除するだけでなく、ID プロバイダー側で従業員を削除します。                                      |
| 退職する従業員のトークンが一覧に残っています。         | トークンの作成者、ワークフローのオーナー、ワークスペース管理者のトークンに関する権限        | 自動化に必要な認証情報をローテーションしてから、退職する従業員のトークンを失効させます。                                   |
| 接続されたアプリケーションに引き続きアクセスできてしまいます。           | 連携先システムのアカウント、プラグインの利用可否、アプリケーションへの権限付与                   | そのシステムでサポートされている管理機能を使ってアクセス権を削除するよう、該当サービスの責任者に依頼します。                                  |

大半の ID プロバイダーは 30～40 分ごとに同期しますが、更新をすぐに反映するものもあります。カスタムロールの変更が反映されるまでに、約 5 分かかることがあります。SCIM の同期を強制的に実行することはできないため、更新の遅延を回避する目的でワークスペースのメンバーを削除して再作成しないでください。

プロバイダーごとの想定時間を過ぎても、アクセス権の削除やグループの更新が完了しない場合は、ID 管理者に次の情報を収集してもらいます。

- 対象のワークスペースと従業員のメールアドレス
- ID プロバイダー、アプリケーションの割り当て、プロビジョニンググループ
- 試みた変更、そのタイムスタンプ、最新の同期状況
- 引き続きレビューが必要な、直接割り当てられたロール、グループに割り当てられたロール、またはトークン

これらの詳細を添えて、ヘルプセンターから [OpenAI サポート](https://help.openai.com/)に問い合わせてください。
退職した従業員にアクセス権が残っている場合は、セキュリティ上の例外として扱い、
組織のインシデントエスカレーション手順に従ってください。

プロバイダーごとのセットアップと同期の動作については、最新の
[SCIM 連携に関するよくある質問](https://help.openai.com/en/articles/10011769-openai-platform-scim-integration-faq)を参照してください。
サインインや ID に関するエラーについては、
[認証のトラブルシューティング](https://help.openai.com/en/articles/10489721-login-and-authentication-faq-s-and-troubleshooting-sso-scim-and-domain-verification)を参照してください。

## 従業員ライフサイクル全体の検証

展開範囲を広げる前に、代表的な従業員のテストアカウントを使い、次の 3 つの移行をすべて検証します。

| ライフサイクルの段階 | 主な責任者                 | 期待される結果                                                                                                            |
| --------------- | ----------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| 入社者          | ID 管理者        | 従業員が正しいワークスペースに参加し、シート、所属グループ、機能へのアクセス権が想定どおりになっています。                                    |
| 異動者           | ID 管理責任者とワークスペースオーナー | 管理者がグループの所属を更新し、ワークスペースオーナーが共有グループのロールを維持しながら、不要になった直接割り当てのロールを削除します。 |
| 退職者          | ID 管理とセキュリティの責任者  | 管理者がワークスペースへのアクセス権を削除し、サポート対象のトークンをレビューし、外部システムへのアクセス権を取り消すか再割り当てします。                       |

各変更の承認者、検証した内容、未解決のアクセス権の例外への対応責任者を記録します。組織の ID 管理とセキュリティのポリシーに従い、定期的にアクセス権をレビューする日程を設定します。
