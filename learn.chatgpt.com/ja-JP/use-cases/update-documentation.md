## はじめに

ドキュメントは、ソース変更の数週間後ではなく、その変更と同時に更新すると、最新の状態を保ちやすくなります。Codex は、コードの変更、テスト、リリースノート、リンク先のイシュー、Pull Request のコンテキストを確認したうえで、既存の構成に沿って対象範囲を絞ったドキュメント更新案を作成できます。

開発者向けドキュメント、README の更新、変更履歴の下書き、移行ノート、ランブックなど、頻繁に変わる動作の反映が必要なあらゆるドキュメントに、このワークフローを使用できます。

## 使用方法

1. ドキュメント化が必要な変更から始めます。

   対象のブランチ、Pull Request、コミット、イシュー、ファイルを共有します。公開ドキュメントの場合は、未公開のロードマップ、顧客の非公開情報、社内限定のコンテキストを含めないことを明示します。

2. 影響を受けるドキュメントを洗い出すよう Codex に依頼します。

   下書きを作成する前に、機能名、設定キー、コマンド、サンプル、関連用語を既存のドキュメントから検索させます。

3. 有用性を損なわない最小限の範囲でドキュメントを更新します。

   Codex には、現在のページ構成、用語、相互リンク、フロントマターを維持させます。対象を絞った注記、サンプル、セクションの更新だけで十分な場合は、大幅な書き直しを避けるようにします。

4. 変更内容を検証します。

   リポジトリに適した書式チェックとドキュメントチェックを実行し、ユーザー向けの各記述を裏付ける根拠を要約するよう Codex に依頼します。

## Codex に提供する情報

| 情報源                               | 役立つ理由                                                               |
| ------------------------------------ | -------------------------------------------------------------------------- |
| 変更されたコードとテスト               | Codex が実際の動作を分析し、必要箇所に絞ったドキュメント更新案を作成できるようにします。 |
| 公開されているリリースノートまたは製品ドキュメント | 公開されている用語、提供状況、機能のステータスに沿ったドキュメントを Codex が作成するのに役立ちます。    |
| Pull Request またはイシューのコンテキスト        | 変更の理由と、ユーザー向けのどの動作が重要かを説明します。   |
| ローカルのドキュメントチェック                    | ドキュメントの公開前に満たすべき具体的な完了条件を Codex に示します。   |

公開リリースノートなど、より多くのコンテキストを追加すると、Codex は非公開のコンテキストや未公開の更新を含めずに済みます。

## 繰り返し使えるワークフロー

リポジトリ全体の規約として、ドキュメントに関する要件を [AGENTS.md](/ja-JP/codex/agent-configuration/agents-md) に追加します。例：

```md
## Documentation

- When user-facing behavior changes, check whether docs, examples, or changelogs need updates.
- Public docs must only include public information or behavior visible in this repo.
- Preserve existing terminology and frontmatter.
- Run the docs formatting and build checks before final handoff.

プロセスの手順がさらに多い場合は、今後の Codex タスクでも同じ情報源の確認、下書き、検証のサイクルに従えるよう、そのプロセスを [スキル](/ja-JP/codex/build-skills) にします。このパターンの詳細については、[ワークフローをスキルとして保存](/ja-JP/codex/use-cases/reusable-codex-skills) を参照してください。
