## はじめに

あるスタックから別のスタックへ移行する際は、Codex を活用して、ルーティング、データモデル、構成、認証、バックグラウンドジョブ、ビルドツール、デプロイ、テスト、さらには言語やフレームワーク自体の規約までを対象に、移行内容を整理し、計画的に実行できます。

ここで Codex が役立つのは、レガシーシステムを棚卸しし、従来の概念と新しい概念の対応関係を整理したうえで、一度に全面的に書き換えるのではなく、チェックポイント単位で変更を反映できるためです。この点は、レガシーフレームワークから移行する場合、新しいランタイムへ移植する場合、または製品を稼働させたまま一方のスタックを別のスタックへ段階的に置き換える場合に重要です。

## 使用方法

1. まず、レガシーパッケージ、フレームワークの規約、ルーティング、データアクセス、認証、構成、ビルドツール、テスト、デプロイに関する前提事項、移行後も維持する必要がある外部インターフェースの契約など、移行範囲を棚卸しします。
2. レガシー環境の概念を移行先スタックに対応付け、直接対応するものがない項目を明示するよう Codex に依頼します。
3. 互換レイヤー、モジュール単位の移植、branch-by-abstraction、境界を一つずつ置き換えるストラングラーパターンなど、段階的な戦略を選びます。
4. 移行自体によってユーザー向けの変更が必要になるまでは、動作を変えずに維持し、例外が生じた場合は明示します。
5. 各マイルストーンの後に、同等性を実証できる必要最小限の検証を実行します。具体的には、lint、型チェック、対象を絞ったテスト、コントラクトテスト、スモークテスト、またはレガシー側の処理経路との比較検証です。
6. 全面的な書き換えの完了を待つのではなく、各チェックポイントの後に、差分と残っている移行リスクをレビューします。

## ExecPlans の活用

OpenAI の [コードモダナイゼーションのクックブック](/cookbook/examples/codex/code_modernization) では、ExecPlans を紹介しています。これは、Codex がクリーンアップの全体像を把握し、目標とする最終状態を明文化して、各回の作業後に検証結果を記録できるようにするドキュメントです。
Codex に複雑な移行を実行させる場合は、システムの各部分について ExecPlan を作成するよう依頼します。これにより、すべての判断と技術スタックの選択が記録され、後からレビューできるようになります。

## 目標との併用

長期間にわたる個々の移行作業では、Codex の作業を導くために [目標](/ja-JP/codex/use-cases/follow-goals) を使用します。目標には、明確な最終状態、同等性チェック、ロールバック方針、停止条件を設定します。
