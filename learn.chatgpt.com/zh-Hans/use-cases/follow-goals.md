## 简介

当您希望 Codex 围绕一个持久目标持续推进，而不是在一个常规轮次结束后停止时，请使用 `/goal`。它适合目标明确、具备验证循环，并且有足够空间让 Codex 自行推进而无需您逐步指导的工作。使用 `/goal` 后，Codex 可以在无需您输入的情况下独立工作多个小时。

使用 `/goal <objective>` 设定目标，使用 `/goal` 查看当前目标；需要控制本次运行时，请使用 `/goal pause`、`/goal resume` 或 `/goal clear`。

如果 `/goal` 未出现在斜杠命令列表中，请启用 `features.goals`
配置（位于 `config.toml` 中）：

```toml
[features]
goals = true

您也可以在 CLI 中运行 `codex features enable goals`，或让 Codex 运行该命令。

## 选择合适的任务

合适的目标，其范围应超出单个提示所能覆盖的内容，但又不能宽泛到像一份没有明确边界的待办列表。它应明确 Codex 要实现什么、不应更改什么、如何验证进展，以及何时停止。

适用场景包括：

- 目标技术栈、一致性检查和约束均已明确的代码迁移
- Codex 可以在每个检查点后运行测试的大型重构
- Codex 可以持续改进可用成果的实验、游戏或原型

避免使用目标来处理一组彼此无关的零散工作。

## 建立工作循环

1. 明确一个目标和一个停止条件。
2. 向 Codex 指明它必须先阅读的文件、文档、议题、日志或计划。
3. 明确用于证明进展的命令或产物。
4. 让 Codex 按检查点推进，并保留简短的进度日志。
5. 运行期间，使用 `/goal` 查看状态。
6. 当运行完成、受阻或需要调整方向时，请暂停、恢复或清除目标。

关键在于约定。Codex 应在开始前就知道“完成”意味着什么。如果目标是迁移，“完成”可能意味着新路径通过契约测试，同时旧路径仍保留回滚方案。如果目标是游戏或原型，“完成”可能意味着应用可以构建和启动，并且与所提供的参考内容或预期行为一致。

  请 Codex 提供帮助：先与它讨论您想要
构建的内容，然后让它直接设定目标并开始工作。

## 让 Codex 独立工作

在目标执行期间，请 Codex 提供简洁的进度报告，以便您放心地让它继续运行。实用的状态更新应说明当前检查点、已验证的内容、剩余工作，以及 Codex 是否受阻。
如果状态变得含糊，请进一步明确目标，而不是添加更多一次性指令。请明确告诉 Codex 接下来哪个检查点最重要、用哪条命令可加以验证，以及在什么情况下应暂停。

Codex 持续推进目标时，可以在无需您查看进展的情况下连续独立工作多个小时。它会在确信已达到停止条件时停止运行，因此，您应将 `/goal` 视为一项无需监控的后台任务。

## 目标示例

### 迁移

无论您是将游戏迁移到新的技术栈、将移动应用迁移到新平台，还是将代码库迁移到新框架，都可以使用 `/goal` 让 Codex 执行迁移：

### 创建原型

无论您是从零开始创建新应用、新游戏还是新功能，都可以使用 `/goal` 让 Codex 完成一个精心打磨的首个版本。您可以使用 PLAN.md 文件指导首个版本的创建，并在其中准确描述您想要构建的内容。

### 提示优化

有评测套件后，您可以使用 `/goal` 根据评测结果优化提示。Codex 可以检查失败项、更新提示、重新运行评测，并不断迭代，直到分数提高或满足您设定的停止条件。
