## 创建一项可供 Codex 随时调用的技能

使用技能向 Codex 提供可复用的指令、资源和脚本，以处理您反复进行的工作。一项 [技能](/zh-Hans/codex/build-skills) 可以保留最初让 Codex 发挥作用的任务、文档、命令或示例。

先从一个可行示例开始：一次对 PR 执行了 cherry-pick 的 Codex 聊天、Notion 中的发布清单、一组实用的 PR 评论，或一条说明上线流程的 Slack 对话串。

## 使用方法

1. 添加您希望 Codex 使用的上下文。

   在您想保留的 Codex 聊天中继续操作，粘贴 Slack 对话串或文档链接，并添加您希望 Codex 记住的规则、命令或示例。

2. 运行起始提示。

   该提示会先指定您想要的技能名称，然后向 `$skill-creator` 提供要保留的任务、文档、PR、命令或输出。

3. 让 Codex 创建并验证技能。

   生成的结果应定义 `$skill-name`，说明技能应在何时触发，并将可复用指令存放在正确位置。

   位于 `~/.codex/skills` 中的技能可在任何代码仓库中使用。您可以提交当前代码仓库中的技能，让团队成员也能使用。

4. 使用该技能，然后在聊天中更新它。

   在下一个 PR、警报、审查、发布说明或设计任务中调用新的 `$skill-name`。如果它使用了错误的测试命令、遗漏了审查规则、跳过了运行手册中的步骤，或生成了您不会发送的草稿，请让 Codex 将相应修正添加到该技能中。

## 提供参考材料

向 `$skill-creator` 提供能够说明技能应如何运作的材料。

| 您已有的内容                                              | 需要添加的内容                                                                                                                                                             |
| ---------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **您希望保留的 Codex 聊天工作流** | 在该聊天中继续操作并输入 `use this chat`。Codex 可以使用聊天上下文、命令、编辑内容和反馈作为起点。                                         |
| **文档或运行手册**                                      | 粘贴发布清单，添加事件响应运行手册的链接，附上 API PDF，或让 Codex 查看您代码仓库中的 Markdown 指南。                                 |
| **团队对话**                                      | 粘贴某人解释警报的 Slack 对话串，添加包含前端规则的 PR 审查链接，或附上说明客户问题的客服对话。 |
| **技能应复用的脚本或命令**             | 添加您希望 Codex 在未来任务中运行的测试命令、预览命令、发布脚本、日志获取脚本或本地辅助命令。                                    |
| **理想结果**                                          | 添加您希望未来任务以其为准的已合并 PR、最终更新日志条目、已采纳的上线说明、已解决的工单、前后对比截图或 Codex 最终回答。         |

如果参考材料位于 Slack、Linear、GitHub、Notion 或 Sentry 中，请通过 [插件](/zh-Hans/codex/plugins) 在 Codex 中连接该工具，并在起始提示中提及它，或将相关内容粘贴到聊天中。

## Codex 创建的内容

大多数技能都从 `SKILL.md` 文件开始。工作流需要时，`$skill-creator` 可以添加更长的参考文档、脚本或资源文件。

## 您可以创建的技能

当未来任务需要阅读同一份运行手册、运行同一个 CLI、遵循同一套审查标准、撰写同一种团队更新，或对同一个浏览器流程进行质量检查时，可以沿用这一模式。例如：

- **`$buildkite-fix-ci`** 会下载失败作业的日志、诊断错误，并提出改动范围最小的代码修复方案。
- **`$fix-merge-conflicts`** 检出 GitHub PR，基于基础分支更新它，解决冲突，并返回确切的推送命令。
- **`$frontend-skill`** 让 Codex 贴合您的 UI 审美，并遵循现有组件、截图质量检查循环、素材选择和浏览器细节优化流程。
- **`$pr-review-comments`** 将审查备注转化为语气恰当、包含 GitHub 链接的简洁行内评论。
- **`$web-game-prototyper`** 确定首个可玩循环的范围、选择素材、调校游戏手感、截取屏幕截图，并在浏览器中进行细节优化。
