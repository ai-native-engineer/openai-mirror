## 시뮬레이터 전체 루프를 Codex에 맡기기

이 사용 사례는 Codex가 전체 루프를 맡을 때 가장 효과적입니다. 올바른 앱 타깃을 선택하고, 시뮬레이터에서 앱을 실행하고, 현재 화면을 검사하고, 재현 단계를 수행하고, 로그와 스크린샷을 수집하고, 필요하면 스택 트레이스를 확인하고, 코드를 패치한 뒤, 같은 경로를 다시 실행해 버그가 사라졌음을 입증합니다.

이 루프를 에이전트 기반으로 유지하려면 [Build iOS Apps 플러그인](https://github.com/openai/plugins/tree/main/plugins/build-ios-apps)을 사용하세요. 이 플러그인의 iOS 디버거 워크플로우는 XcodeBuildMCP를 기반으로 하므로 Codex는 부팅된 시뮬레이터와 상호작용하며, 일반적으로 사람이 직접 수집하는 것과 동일한 증거를 수집할 수 있습니다.

XcodeBuildMCP에 시뮬레이터 자동화, UI 자동화, 디버깅, 로깅 워크플로우를 구성하면 Codex가 재현-디버깅-검증 루프 전체를 맡을 수 있습니다. Codex가 아직 프로젝트, 스킴, 시뮬레이터를 선택하지 않았다면 먼저 이를 찾게 하고 나머지 세션 동안 해당 설정을 재사용하도록 요청하세요.

## XcodeBuildMCP의 기능 활용하기

Codex에 사용하도록 요청할 수 있는 실용적인 기능 그룹은 다음과 같습니다:

- 프로젝트 및 시뮬레이터 탐색: Codex가 사용할 앱 타깃과 시뮬레이터를 이미 알고 있는지 확인하고, Xcode 프로젝트나 워크스페이스를 찾고, 스킴 목록을 확인하고, 시뮬레이터를 찾거나 부팅하며, 이후 빌드/실행 단계에서도 이 설정이 유지되도록 합니다.
- 빌드 및 실행 제어: 활성 앱 타깃을 빌드하고, 시뮬레이터용 빌드를 설치하여 실행하고, 필요하면 로그 수집을 활성화한 상태로 재실행하며, Codex가 앱별 런타임 로그를 검사해야 할 때는 앱 번들 ID를 확인합니다.
- UI 검사 및 상호작용: 화면의 접근성 계층 구조를 읽고, 스크린샷을 찍고, 컨트롤을 탭하고, 필드에 입력하고, 목록을 스크롤하며, 화면 가장자리 스와이프나 기타 시뮬레이터 제스처를 수행합니다.
- 로그 및 디버거 상태: 시뮬레이터 로그를 스트리밍하고, 실행 중인 앱에 LLDB를 연결하고, 중단점을 설정하고, 스택 프레임과 로컬 변수를 검사하며, 충돌이나 멈춤을 더 자세히 조사해야 할 때 디버거 명령을 실행합니다.

중요한 습관은 Codex가 탭하기 전에 뷰 트리를 검사하도록 하는 것입니다. XcodeBuildMCP는 접근성 계층 구조와 좌표를 제공하므로 Codex는 원시 화면 위치를 추측하는 대신 안정적인 레이블이나 요소 ID를 우선 사용할 수 있습니다.

## 모호한 버그를 재현 가능한 스크립트로 만들기

iOS 디버거 스킬은 프롬프트에 구체적인 버그 하나와 예상 결과 하나를 제시한 다음, Codex가 앱을 조작하고 자율적으로 증거를 수집하도록 할 때 가장 효과적입니다. 로그인, 딥 링크 또는 테스트 픽스처가 필요하다면 이를 한 번만 알려 주고, 해당 정보가 없어 진행할 수 없을 때만 Codex가 일시 중지하도록 요청하세요.

## 실용적인 팁

### 수정뿐 아니라 증거도 요청하기

Codex가 버그를 설명할 때 사용한 정확한 시뮬레이터와 스킴, 스크린샷, 로그 일부, 스택 세부 정보를 요청하세요. 그러면 "이렇게 하면 수정될 것 같습니다."라는 설명만 있는 경우보다 최종 패치를 훨씬 쉽게 검토할 수 있습니다.

### 좌표보다 접근성 레이블 우선 사용하기

컨트롤에 안정적인 레이블이나 접근성 식별자가 없어 Codex가 좌표로 탭해야 한다면 그 사실을 명시하도록 요청하세요. 이는 UI 테스트 용이성을 조금 개선하는 작업도 버그 수정에 포함해야 한다는 신호인 경우가 많습니다.

### 실행 한 번에 버그 하나만 다루기

시뮬레이터 기반 디버깅 루프는 강력하지만, 프롬프트 하나가 실패 유형 하나에 집중할 때 더 신뢰하기 쉽습니다. 인접한 이슈로 범위를 넓히기 전에 Codex가 하나의 재현-수정-검증 주기를 완료하도록 하세요.
