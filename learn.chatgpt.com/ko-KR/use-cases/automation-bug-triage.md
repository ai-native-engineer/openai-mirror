## 사용 방법

Sentry 알림, Linear 이슈, GitHub 이슈, PR 검사, 배포 로그, 지원 티켓, Slack 스레드 등 버그가 이미 보고되는 곳을 Codex가 확인하도록 하세요. 먼저 수동으로 한 번 점검하고 채팅에서 보고서를 다듬은 다음, 예약 실행하세요.

전체 트리아지 과정을 하나의 Codex 채팅에서 진행하세요:

1. 점검을 한 번 실행해 목록 초안을 받으세요.
2. 같은 채팅에서 목록을 검토하고 피드백을 제공하세요.
3. 해당 채팅에서 트리아지 작업을 예약하세요.
4. 선택 사항: 보고서의 품질이 충분하다고 판단되면 Codex에 Linear 이슈, Slack 업데이트, GitHub 댓글 또는 인계 메모의 초안을 작성하도록 요청하세요.

시작하기 전에 Sentry, Slack, Linear, GitHub 등 Codex에 필요한 [플러그인을](/ko-KR/codex/plugins) 설치하세요. 시작 프롬프트에서 대괄호로 표시된 플러그인 목록을 실제 `@` 플러그인 칩으로 바꾸세요. 그런 다음 대괄호로 표시된 각 소스를 검색할 정확한 위치로 바꾸세요. 예를 들면 Sentry 프로젝트 또는 알림 URL, Slack 채널 또는 스레드, Linear 팀, 보기 또는 쿼리, GitHub 레포지토리, 이슈 쿼리 또는 PR 검사, 배포 링크, 로그 파일, 지원 요청 대기열 또는 대시보드입니다.

## 1단계: 점검 실행

테스트, 레포지토리 도구, 빌드 검사, CI 실패 등 로컬 컨텍스트가 도움이 되는 경우에는 버그가 속한 레포지토리에서 Codex를 시작하세요. 플러그인, 커넥터, MCP 서버, 링크, 내보내기 파일, 붙여 넣은 로그 또는 첨부 파일을 통해 버그 소스에 접근할 수 있다면 어떤 레포지토리에서든 점검을 실행할 수 있습니다.

먼저 위의 시작 프롬프트를 실행하세요. 점검에 필요한 플러그인과 소스만 남기세요.

예를 들어 완성된 프롬프트에는 점검에 사용할 플러그인과 정확한 대기열, 채널 또는 레포지토리를 지정할 수 있습니다.

## 2단계: 유용한 보고서 만들기

자동화하기 전에 보고서를 매일 확인할 가치가 있을 만큼 유용하게 다듬으세요.

유용한 첫 점검 결과는 다음 조건을 충족합니다:

- 유의미한 버그가 P0부터 P3까지 우선순위순으로 정렬되어 있습니다.
- 중복 보고서가 하나의 버그로 그룹화되어 있습니다.
- 각 버그에 근거 링크나 짧은 인용이 있습니다.
- 추정은 관찰된 사실과 구분되어 있습니다.
- 각 버그에 권장하는 다음 조치가 간략히 적혀 있습니다.

예약하기 전에 같은 채팅에서 보고서를 다듬으세요. Codex에 다음과 같이 요청할 수 있습니다:

- 목록의 순위를 정하기 전에 소스를 하나 더 확인하세요.
- 팀이 이미 알고 있는 노이즈 알림은 제외하세요.
- P0 및 P1 버그만 반환하세요.
- Slack의 버그 보고, Sentry 알림, GitHub의 검사 실패가 동일한 버그를 가리키면 하나로 병합하세요.
- 각 버그에서 가장 적합한 링크 하나만 표시하세요.
- 다른 사람이 이슈를 재현하거나 적절한 담당자에게 전달할 수 있도록 충분한 근거를 추가하세요.

## 3단계: 자동화

필요할 때 실행한 보고서가 유용하다면 같은 채팅에서 [해당 트리아지 작업을 예약하세요](/ko-KR/codex/automations#schedule-a-task-inside-a-chat). Codex는 채팅에서 다듬은 내용을 활용해 반복 실행에 사용할 프롬프트를 작성할 수 있습니다.

## 4단계: 후속 작업 전달

예약 보고서가 충분히 유용해지면 후속 작업을 어디로 전달할지 결정하세요. Codex는 팀 채널에 올릴 Slack 업데이트 초안을 작성하고, 추적하려는 버그의 Linear 이슈를 작성하고, 검사에 실패한 PR에 남길 GitHub 댓글을 작성하거나, 온콜 담당자를 위한 인수인계 메모를 만들 수 있습니다.
